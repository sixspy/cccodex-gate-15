# 闸口事件湖仓台

码头闸口扫描先落在贴源层，原文照收。建层员选定业务日，按事件字典把扫描收成明细层：进闸、出闸、倒箱。字典里没有的事件码、箱号不合法或时间读不出的扫描留在剔除清单，不进明细。

一批扫描中途失败时，落成前要先定落批办法。办法只有两种，写定即收束、当日禁止改口：

- **整批回滚**：整批一笔不进明细；
- **成功先落库、失败进死信**：合法扫描进明细，失败扫描进死信队列。

编排带上的办法跟当日落批设置不合，记「落批办法偏了」，失败批次不入库。两名仓管同时落同一个失败批次，行锁串行化后只留一份与设置相符的结果，后到的记「落批争用」。批次号为空的散扫只进剔除清单，不进死信队列。落批设置没收束的日子，不准编排失败批次。

这里不管堆存量，只处理扫描事件怎么分层、失败批次怎么落批。

## 落批接口

| 接口 | 作用 |
|------|------|
| `GET /api/landing` | 同轮核齐：落批设置、落批列表、失败详情、死信队列一个快照返回（REPEATABLE READ） |
| `POST /api/landing/settings` | 仓管收束当日落批办法，body：`{"biz_date","strategy"}`，strategy 取 `ROLLBACK` 或 `PARTIAL`，重复收束 409 |
| `POST /api/landing/orchestrate` | 仓管编排失败批次，body：`{"batch_id","strategy"}`；办法偏了、争用、未收束均 409 并写审计留痕 |

## 测试

本地没有 PostgreSQL 时，用内存模拟连接跑全部落批规则（真实 SQL 语义由 FakeConn 复刻）：

```bash
python -I tests/test_landing.py
```

`SELECT ... FOR UPDATE` 的真实并发阻塞语义需要在 PostgreSQL 上验证，内存测试只覆盖争用状态机。
